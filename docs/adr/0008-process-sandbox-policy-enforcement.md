# ADR 0008 — Process sandbox policy enforcement

Status: accepted as the design (2026-09-24); enforcement ships only after the review and adoption gates below pass
Owner: IPC lane. Depends on ADR 0005 and the demand-driven transfer amendment to ADR 0007.

## Context and boundary

`amazing_process::SandboxPolicy` currently records a role, file roots, and two booleans; `ProcessHost::spawn` uses an ordinary `Command`. Neither enforces isolation. IPC-3's Windows frame path has the **browser** duplicate a read-only mapping from its known renderer child, while Linux passes one descriptor on a private Unix socket after `AcquireFrame`. The sandbox must preserve these channels without giving the renderer a browser process handle or general file/network access.

This ADR specifies the intended policy, not an implementation or a claim that the syscall list is complete. Untrusted web content remains unsupported for sandboxed production use until the platform gates below pass. A failed sandbox setup must fail the child launch; it must never silently run that role unsandboxed.

## Decision to review

The browser remains the privileged broker and UI owner. Each renderer gets a separate identity, restricted resource view, IPC channel, and lifecycle container. The network process owns outbound sockets and HTTP state, but no arbitrary file capability. A GPU process, when introduced, gets device access without network or arbitrary file access. Utility tasks receive separate profiles tied to their operation; there is no universal utility allowlist. A compromised renderer may send requests only over its assigned IPC endpoints. The broker checks request provenance, site assignment, URL scheme, byte limits, and any file grant before forwarding.

Separate **bootstrap** from **steady state**: create the child with only intended inherited handles/descriptors; establish stdio IPC and the frame side channel; verify the version/role/nonce handshake; prepare required resources; enter the final restricted policy before processing page-controlled input. If the platform requires restrictions at process creation, launch restricted first and make its bootstrap work within that policy. Never use a period of unrestricted page processing as a workaround. Do not treat a nonce or a Rust `SandboxPolicy` value as an OS security boundary.

| Role | Allowed steady-state capabilities | Explicitly excluded |
|---|---|---|
| Browser | UI, process/job ownership, profile and approved user files, brokered network requests, validated read-only frame mapping | No untrusted document execution in the privileged process once renderer adoption lands |
| Renderer | Own executable/runtime mappings, read-only packaged fonts/assets or brokered font bytes, stdin/stdout IPC, one frame channel, anonymous page-file/memfd frame creation, private scratch memory | Outbound/inbound TCP or UDP, arbitrary file open, registry/profile access, device access, other-process handles, child process creation |
| Network | Outbound DNS/TCP/TLS through the Fetch service, IPC to browser/authorized renderer, read-only trust roots, bounded cache/cookie store only through brokered storage grants | UI, GPU, camera/microphone, arbitrary local paths, frame handles, child process creation, listening sockets except a separately reviewed loopback test profile |
| GPU (future) | IPC, specifically enumerated graphics adapter/device handles and shader cache grant | General network, web files, process creation, frame ownership outside assigned compositor protocol |
| Utility (future) | IPC plus a task-specific read-only input or scratch grant | Network/device/process capabilities unless a new task profile explicitly approves them |

`file_roots` alone cannot express file authority safely: a string path is vulnerable to path substitution and does not constrain already open descriptors. The browser should resolve and open approved files and pass a narrow read-only handle or bytes; any directory grant needs a separately reviewed path traversal and reparse/symlink policy. Renderer page URLs never become local file grants by themselves.

## Windows profile

Use an **AppContainer** identity per renderer isolation domain, with no network capabilities; use a distinct AppContainer for the network role with only the outbound capability proven necessary. Evaluate Less Privileged AppContainer for renderers after font/loader compatibility is measured. A restricted primary token (disabled SIDs, removed privileges, low integrity) may further narrow each child, but a restricted token alone is not the chosen renderer boundary. There must be no fallback to an ordinary user token if AppContainer setup or ACL preparation fails. Create the profile and grant only the executable/runtime dependencies and named IPC objects it needs; the browser retains profile/ACL management. [Microsoft's AppContainer launch guide](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) describes the security-capability creation attribute; [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation) describes its file, network, process, and device boundaries.

Launch suspended or under an equivalent race-free setup path, assign a per-child job before resume, and keep the job handle in the browser. Set kill-on-job-close, one active process, no breakaway, and bounded memory/CPU limits measured against real pages. Apply child-process creation restriction and compatible process mitigations after platform validation; do not enable dynamic-code or Win32k restrictions blindly while the JS/runtime or font stack still needs them. A job controls lifetime and resources; the token/AppContainer controls access. [Job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and [process creation attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) document these mechanisms.

Inherited handles must be an explicit `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`: stdin read, stdout write, optional stderr sink, and only role-specific bootstrap objects. Clear ambient inheritance elsewhere. For IPC-3 frames, the browser retains the renderer child process handle with `PROCESS_DUP_HANDLE` (plus minimal query/synchronization rights for lifecycle), uses the renderer-supplied numeric handle only after validating its child identity and generation, duplicates it as `FILE_MAP_READ`, and closes it on release/crash. The renderer receives no browser process handle. Job handles, profile/secret files, and network sockets are never inherited by a renderer. The process-handle right needed for IPC-3 is a browser-side trust cost that requires explicit review; if it cannot be constrained acceptably, redesign frame transfer before enabling the sandbox.

## Linux profile

Create user and mount namespaces for each sandboxed child; map only its unprivileged UID/GID, make mount propagation private, provide a minimal read-only runtime tree and role-specific bind mounts, and make writable scratch an isolated size-bounded tmpfs. A renderer additionally enters a network namespace with no configured external interface. The network process needs access to host networking (or an explicitly provisioned equivalent); it still has no arbitrary filesystem view. Use a PID namespace only with a reviewed init/reaping arrangement; it is not required for the first enforceable profile. Close every descriptor except the role table below before handing over page-controlled work. Namespace setup can be unavailable under host policy; that is a launch failure, not permission to fall back. [Linux user namespaces](https://man7.org/linux/man-pages/man7/user_namespaces.7.html), [mount namespaces](https://man7.org/linux/man-pages/man7/mount_namespaces.7.html), and [network namespaces](https://man7.org/linux/man-pages/man7/network_namespaces.7.html) describe the isolation primitives.

Set `PR_SET_NO_NEW_PRIVS`, drop all capabilities, then install architecture-checked seccomp-bpf with a default deny action. Install before any untrusted work; apply to all threads and verify synchronization. Distinguish startup syscalls from steady-state syscalls; do not expand steady-state policy to accommodate a loader or test harness that can complete setup earlier. Seccomp filters syscall numbers/arguments and cannot validate path strings or replace mount/FD isolation. [Kernel seccomp guidance](https://docs.kernel.org/userspace-api/seccomp_filter.html) and [seccomp(2)](https://man7.org/linux/man-pages/man2/seccomp.2.html) cover `no_new_privs` and filter installation.

Provisional **x86_64 Linux steady-state** allowlist to validate by trace and negative tests (other architectures need a distinct reviewed table):

| Role | File descriptors retained | Additional syscall families beyond the measured Rust/libc baseline |
|---|---|---|
| Renderer | IPC read/write, private `AF_UNIX` frame socket, optional log sink, explicitly granted read-only font/runtime files | `memfd_create`, `ftruncate`, `mmap`/`mprotect`/`munmap`, `sendmsg`/`recvmsg` **only on the inherited Unix FD** for one requested frame; no `socket`, `connect`, `accept`, `openat`, `execve`, `ptrace`, or namespace creation after lockdown |
| Network | IPC, resolver/trust-root read-only FDs or narrow mounts, outbound sockets created after lockdown, bounded storage FD if approved | `socket` restricted to `AF_INET`/`AF_INET6` TCP/UDP and resolver-required `AF_UNIX`, `connect`, `sendto`/`recvfrom`, `sendmsg`/`recvmsg`, `getsockopt`/`setsockopt`, `shutdown`, `getpeername`/`getsockname`; `openat` only if a path-safe mount view has been separately proven; no `bind`/`listen`/`accept` in production |
| GPU (future) | IPC and individually granted DRM/render device FDs | `ioctl` only for enumerated device requests after driver-specific review; no blanket `ioctl` allow |
| Utility (future) | IPC and task-granted FDs | Task-specific delta; default is no network/device or process creation |

The shared runtime baseline is expected to include `read`, `write`, `close`, `fstat`/`newfstatat` on inherited FDs, `lseek` where needed, `mmap`/`mprotect`/`munmap`, `brk`, `futex`, `clock_gettime`, `getrandom`, `rt_sigaction`/`rt_sigprocmask`/`rt_sigreturn`, `exit`/`exit_group`, `getpid`/`gettid`, and scheduler/timer calls actually seen under the pinned toolchain. Threads, `clone`/`clone3`, `epoll*`, `poll`/`ppoll`, `fcntl`, `prlimit64`, and `io_uring*` are **not preapproved**: trace their actual use and constrain or omit them. Network DNS/TLS, Rust thread startup, media codecs, font loading, and GPU drivers can change the list. For FD-specific operations that seccomp cannot reliably pin to a capability, rely on the inherited-FD table and namespace isolation as well; do not claim the table alone enforces the boundary.

## Review and adoption gates

1. Record a per-role, per-platform capability inventory from real launch, document, font, frame, and network fixtures, including opened paths, inherited handles/FDs, syscalls, Windows token SIDs/privileges and job settings. Pin OS/toolchain/architecture and separately record bootstrap and steady-state traces. Turn each unexpected access into a reviewed policy change or a broker request.
2. Review launcher and platform unsafe code, handle rights/ACLs, namespace and seccomp order, crash cleanup, and confused-deputy checks with a security reviewer. A deny test must show a renderer cannot open user files, connect a socket, spawn a child, or obtain another process handle; the network role cannot open an arbitrary user path or receive a frame capability.
3. Pass IPC-3 frame parity and leak/crash gates under the restricted profiles on Windows and Linux, including demand-driven `AcquireFrame`/`Superseded` and the 256 MiB budget. Check process/job or namespace teardown after browser and child crashes.
4. Run the driver/network adoption parity gates in ADR 0009. Enable sandboxed page loads only after all access denials and functional gates pass on both target platforms. macOS needs a separate profile and review.
