# ADR 0005 — Multi-process architecture and a typed IPC layer

Status: accepted (2026-09-24)

## Context

AGENTS.md lists "no sandbox, no multi-process" as a locked non-goal to revisit
before Stage 2, and Stage 3 of the roadmap is a Chromium-style process model:
browser, renderer, network and GPU processes, sandboxing and site isolation.
Nothing today depends on process boundaries, so the IPC layer and process host
can be built now as new crates, beside the single-process engine, and adopted
later without blocking Stage 1.

## Decision

- **`crates/amazing-ipc`**: typed message channels. Interfaces are Rust traits
  whose messages are generated by a declarative macro. Messages use a
  versioned, bounds-checked binary serialization with handle passing, and
  pipes are ordered, associated and cancellable. Transport starts std-only
  over child-process stdio pipes and loopback, plus an in-process transport
  for tests. `#![forbid(unsafe_code)]`. Shared memory and OS handle
  duplication come later, as a separately reviewed platform layer.
- **`crates/amazing-process`**: process roles (browser, renderer, network,
  GPU, utility), a launcher and child bootstrap handshake, liveness, crash
  detection and restart, and the site-to-renderer assignment policy for site
  isolation. Sandbox policy is a typed description, enforced later per
  platform in a reviewed crate.
- The engine stays single-threaded inside each process (locked decision 1).
  Multi-process is how parallelism and isolation arrive, not threads in the
  renderer.
- Owner: the new `ipc` lane.

## Consequences

The "no multi-process" non-goal is replaced by this ADR. The driver keeps
running single-process until an adoption ticket moves the network service,
then the renderer, behind IPC. Every message type is fuzzed (Stage 3 gate).
