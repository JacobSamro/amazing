# ADR 0009 — Driver adoption of the network process

Status: accepted (2026-09-24); each step lands behind its own parity gate
Owner: IPC lane for the IPC contract; integrator-assist for driver edits. Depends on ADR 0005, ADR 0008, and the IPC-2 network demo.

## Current seam

`amazing-process` has `Role::Network`, `NetworkRequests::{start_request,poll_request,cancel_request}`, and a `NetworkService` adapter. IPC-2 proves a renderer can load stylesheet and image bytes through it. Its `StartRequest` contains only `url` and `base_url`; `ResponseHead` contains only status and final URL; `fetch_resource` returns a body only after a 2xx status and limits it to one IPC frame. `NetworkEndpoint` currently creates one actor thread, queues a fully materialized response as 32 KiB chunks, and uses a default `ClientContext`. This is a demo transport contract, not a driver-compatible Fetch boundary.

The driver has no `amazing-process` dependency. It directly fetches network resources in `page.rs` (CSS, image, web font and Windows/WPT font files), `gui.rs` (top-level streaming document, CSS and scripts), `dom_host.rs` (JS `fetch()`), `cmd/js.rs` (external scripts), `cmd/net.rs` (fetch and fetch-parse), and `document.rs` (HTTP document input). The rendering CLI also reads local page/CSS paths in `cmd/parse.rs`. Those call sites cross different trust boundaries; replacing every `amazing_net::fetch` with the current `fetch_resource` would lose response headers, content type/charset, non-2xx responses, request options, streaming, and file behavior.

## Proposed contract and ownership

The browser owns the navigation, site assignment, allowed file roots, cookie/storage profile, and network process lifecycle. A renderer supplies a request plus its authenticated process/site identity; it never chooses its own trusted origin, cookie site, CSP, or local file root. The network role constructs `ApiRequest` and `ClientContext` from browser-validated fields, and owns DNS, sockets, TLS, redirects, cookies and cache. The browser delivers document bytes and validated response metadata to the renderer. The renderer requests HTTP(S) subresources through a browser-associated channel; any `data:` resource is decoded locally with a byte cap, and `file:` or bare paths require an explicit browser file grant. The first adoption can keep the existing in-process driver path behind an explicit mode switch while parity is measured. Sandbox enforcement is a separate gate under ADR 0008; process separation alone is not a sandbox claim.

Revise the typed IPC contract before driver integration:

| Message or behavior | Required fields and invariant |
|---|---|
| Start | Request ID assigned by network role; resolved URL, method, bounded headers/body, destination, mode, credentials, redirect/cache policy, referrer, response-byte limit, browser-derived origin/site/CSP context and navigation epoch. Reject malformed values before `NetworkService::start`. No serialized Rust structs or ambient defaults as a security shortcut. |
| Head | Final URL, status, reason if exposed by the driver, ordered response headers including `Content-Type` with charset, and response type/redirect outcome. Preserve header semantics needed by HTML/XML selection, JS `HostResponse`, and CLI `fetch -i`. |
| Body | Chunks with request ID and bounded total bytes; pull or credit-based flow control so a slow renderer cannot make the network actor queue an unbounded full body. Preserve byte order and decoded-body semantics. Streaming consumers receive chunks before completion. |
| Complete/cancel | Exactly one terminal result per request. Cancellation on navigation replacement, renderer disconnect, timeout, or browser shutdown aborts `NetworkService` work and releases queued bytes. A late event from an old navigation epoch is discarded. Process crash gives callers an explicit network error and a browser-controlled restart; never replay a non-idempotent request automatically. |

Do not silently substitute `ClientContext::default()` or use the URL's own origin for a cross-origin request. The driver and Fetch owners must agree on the context fields and on how `ApiRequestInit` represents methods, bodies, headers and response limits. The current JS host response expects headers, status, URL and text; streaming document parsing needs raw bytes plus transport content type. Reuse these public domain types at the driver edge where appropriate, but keep IPC wire types versioned and bounded.

## Integrator-assist execution order

1. **Baseline and interface handoff.** Freeze the current driver executable/source revision and pinned WPT selection. Record direct-fetch call sites above and expected CLI, document, JS, CSS, image and font behavior. Request the IPC contract extensions from the IPC lane and any Fetch context/streaming changes from its owning lane; integrate only after those public APIs land. Add `amazing-process` as a driver dependency through the integrator-owned root/driver manifests.
2. **Driver network session.** Add a single driver-owned `NetworkSession` or equivalent adapter that launches `--type=network` through `ProcessHost`, owns `NetworkProxy`, polls liveness, and exposes bounded response/stream operations. Give it a browser-generated navigation epoch and request context. The driver binary handles the network child dispatch in `main.rs`; `ipc-demo-child` is a test artifact, not the installed browser child. Verify child bootstrap/teardown and a local HTTP fixture before changing page rendering.
3. **Top-level document.** Route HTTP(S) reads in `document.rs` and `gui.rs::render_page` through the session, preserving stream chunks and the exact `Content-Type`/charset sent to `parse_streaming_document` or `parse_document_bytes`. Keep local CLI page/CSS reads under the browser's explicit file policy. Compare HTML/XML selection, parse errors, exit codes and body bytes with the baseline; no HTML fallback on XML errors.
4. **Subresources and JS.** Pass the session through one resource-loader seam used by `page.rs` (stylesheets, images and web fonts), `gui.rs` CSS/scripts, `cmd/js.rs` external scripts, and `dom_host.rs::fetch`. Preserve each caller's byte cap, relative URL resolution, response headers and JS-visible status. Use browser-granted font files and WPT fixture paths; do not teach the network role to open arbitrary renderer-supplied paths. Refuse unsupported schemes explicitly. Route renderer requests through the browser-associated network channel once the renderer path is adopted.
5. **CLI and failure behavior.** Migrate `cmd/net.rs` `fetch` and `fetch-parse`, preserving reason phrase/headers/body output and status handling. Exercise cancellation on navigation and child death; surface one stable error and restart only under a browser policy. Verify that a renderer cannot select another tab's request ID or origin and that a stale completion is ignored.
6. **Opt-in parity and rollout.** Run the same fixture corpus in direct and process modes: HTTP redirects, non-2xx, charset/MIME including XML and `+xml`, script `fetch()` headers, CSS/images/fonts, `data:` URLs, local file grants, large/slow/chunked bodies, cancellation, network crash/restart and WPT root mapping. Compare response bytes/headers, CLI output, pixels and classifications on the pinned Windows gate; record every divergence. Then run driver crate plus workspace nextest/doctests and the lane's before/after corpus on Windows. Turn process mode on by default only after zero unexplained losses and ADR 0008's security gate; retain the explicit direct mode as a diagnostic parity oracle until its removal is separately reviewed.

## Cross-lane handoff

Integrator-assist owns driver call-site changes and gate evidence. IPC owns the message/version changes, bounds, cancellation and process-host lifecycle API. Fetch/net owners review semantic mapping of request context, redirects, streaming, cache/cookies and file behavior. The integrator owns root manifest changes and the eventual default-mode switch. Driver steps are executed by integrator-assist in the order above, each after the IPC contract extensions they need have landed.
