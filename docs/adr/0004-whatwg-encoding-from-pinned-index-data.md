# ADR 0004 — The WHATWG Encoding Standard from pinned index data

Status: accepted (2026-09-23)

## Context

HTML-2 landed a bounded four-decoder bridge (UTF-8, UTF-16LE/BE and
windows-1252-class single byte). Real pages and several WPT areas
(`encoding/`, `html/syntax`, form submission, `TextDecoder`) need every
encoding in the WHATWG Encoding Standard, including the multi-byte legacy CJK
encodings: GBK and gb18030, Big5, EUC-JP, ISO-2022-JP, Shift_JIS and EUC-KR.

Options: (1) pinned WHATWG index data plus hand-written decoders and
encoders; (2) a vetted `encoding_rs` adapter; (3) keep four decoders.

## Decision

Option 1. A new std-only crate, `crates/amazing-encoding`:

- Index tables are generated by a checked-in script from the pinned WHATWG
  `indexes.json` (recorded revision and SHA-256), in the same pattern as the
  PSL and the UTS #46 IDNA tables. This is pinned **data**, not a crate
  dependency. The crate stays std-only with `#![forbid(unsafe_code)]`.
- It covers the Standard's decoders and encoders, streaming with bounded
  state, the label lookup, BOM sniffing, and replacement/fatal error modes.
- Consumers adopt it through their owners: the html parser (replacing the
  HTML-2 bridge), Fetch/XHR text decoding, and later `TextDecoder`/
  `TextEncoder` through the bindings.
- Owner: the `html` lane, which built the HTML-2 decoders.

## Consequences

The four-decoder bridge is retired once the html lane adopts the crate. WPT
`encoding/`'s data-driven tests become the gate.
