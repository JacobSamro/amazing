# JS34: Named function-expression binding assignment

A named function expression creates an initialized immutable self binding with `CreateImmutableBinding(name, false)`. Sloppy writes ignore the new value; strict writes throw. Ordinary const/import/class bindings continue to force strict assignment semantics. The engine's prior single `mutable` bit incorrectly treated both kinds as const.

`Binding.immutable_strict` records the missing distinction. Every existing Binding constructor initializes it true. The dedicated `EnvHandle::declare_function_name` API creates a lexical immutable cell and sets only that fresh cell's flag false. AST function-expression construction and VM `MakeNamedFunction` use it. Lexical PutReference passes the current execution strictness through `assign_with_strict`; existing internal `assign` retains strict behavior. Import and TDZ errors remain prior to immutable write handling, and successful sloppy rejection does not mutate or replace the cell.

All actor/worker/environment snapshots use existing cloned EnvHandle/BindingCell strong ownership or derived Binding clones, so the scalar remains attached to the original cell. No cell serialization schema or tracing collector exists in this fixed engine. Runtime mapped arguments' mutable writes and live import targets are unchanged. VM23's separately owned GDI constructors must initialize the additional scalar true and preserve its global script-cell lookup branch when combining.

Parent and VM owner granted exactly the scalar/constructor tags, strict-aware Env assignment, lexical PutReference and two named-expression declaration consumers. No GDI/FDI/factory/scheduler changes. This is independently written metadata and execution glue against [Declarative SetMutableBinding](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-declarative-environment-records-setmutablebinding-n-v-s), with no copied upstream code.
